= Learn about global namespace for grid federation
:icons: font
:imagesdir: ../media/

[.lead]
Configure a global namespace across multiple StorageGRID systems to enable unified S3 bucket access and automatic request routing. This procedure includes setting S3 endpoint domain names, assigning unique grid regions and CNAMEs, and creating grid federation connections with global namespace enabled.

== What is global namespace?

A global namespace allows tenant access to buckets across multiple StorageGRID systems. When global namespace is enabled on grid federation connections, S3 CreateBucket and ListBuckets requests targeting the global namespace endpoint can be sent to any grid's load balancer endpoint and are automatically routed to the correct grid based on the signing region in the request.

StorageGRID doesn't enforce unique bucket names across grids in the global namespace, so buckets with the same name can exist on different grids. The signing region in the request is used to determine which grid owns the bucket and should receive the request.

For example, if Grid A uses region `us-east-1` and Grid B uses region `us-west-1`, a CreateBucket request sent to any grid with `--region us-west-1` is automatically routed to Grid B.

For more information about grid federation, refer to link:grid-federation-overview.html[What is grid federation?].

== Global namespace example

Technically it only routes Create bucket and LIST bucket requests between grids, and does not do any other routing.

The customer is supposed to setup a DNS resolver to do the DNS mapping of buckets URLs to a specific grid.

Grid 1

* Default region: region-1
* Default CNAME: s3.grid1.netapp.com
* Global endpoint: s3.netapp.com

Grid 2

* Default region: region-2
* Default CNAME: s3.grid2.netapp.com
* Global endpoint: s3.netapp.com

Grid 3

* Default region: region-3
* Default CNAME: s3.grid3.netapp.com
* Global endpoint: s3.netapp.com

Create Bucket + List bucket operations

If I create a bucket (bucket123) with region region-2 (and targeting the global endpoint s3.netapp.com) no matter which grid gets the request it will create it on Grid 2.

Create bucket bucket123.s3.netapp.com with --region region-2 will route to Grid 2.

Similarly, listing the buckets will route to whatever --region you specify.

List buckets for --region region-3 will route to Grid 3

However you won't be able to have a "global view" of all the buckets (yet, in 12.1) you can only list the buckets for each grid individually using the region routing.

//
Bucket-specific + general object operations

Once the bucket is created on a given grid, a customer's DNS resolver should (if they implement it correctly.. we don't provide instructions on how they're supposed to set one up), resolve the bucket URL to the bucket + grid cname.

In the example above, the DNS resolver should resolve bucket123.s3.netapp.com to bucket123.s3.grid3.netapp.com (bucket + grid's cname). Then all requests are directly sent to that grid and we do not do any routing of these requests for them.

So a PUT object to bucket123.s3.netapp.com resolves to bucket123.s3.grid3.netapp.com

== Requirements for configuring global namespace

* All grids in a global namespace must have grid federation connections with global namespace enabled between every pair of grids.
* The maximum number of grids that can participate in a single global namespace is 11 (the local grid and 10 remote grids).
+
NOTE: This 10-grid limit is constrained by the maximum total number of grid federation connections supported by a StorageGRID deployment. The total connection limit applies to *all* grid federation connections in the deployment, including those without global namespace enabled, so you must ensure that the fully connected global namespace and any additional grid federation connections together do not exceed this overall limit.

* S3 clients must use signature version 4 (SigV4) authentication. Anonymous and signature version 2 requests aren't supported for global namespace routing operations.

== Number of required connections

In a global namespace, every pair of grids must be connected. The number of connections required depends on the number of grids:

[cols="1a,1a" options="header"]
|===
| Number of grids | Number of connections required

| 2
| 1

| 3
| 3

| 4
| 6

| 5
| 10

| _n_
| _n_ × (_n_ − 1) / 2

== S3 behavior with global namespace

After global namespace is fully configured, the following S3 behavior applies.

=== Region enforcement

All S3 requests to the global namespace endpoint, except link:../s3/operations-on-buckets.html[CreateBucket] and link:../s3/operations-on-the-service.html[ListBuckets], require that the signing region in the V4 authentication header matches the grid's default region.

* If the signing region doesn't match, the request is denied with the following error:
+
----
An error occurred (AuthorizationHeaderMalformed) when calling the <operation> operation: The authorization header is malformed; the region '<signing-region>' is wrong; expecting '<grid-default-region>'
----

* Region enforcement applies to all buckets on the grid, including buckets that were created before global namespace was enabled.

* Region enforcement applies only to V4 authentication requests. Anonymous and V2 requests aren't subject to region enforcement.

=== CreateBucket routing

CreateBucket requests sent to the global namespace endpoint (`s3.example.com`) can be directed to any grid's load balancer endpoint. The request is automatically routed to the grid whose default region matches the signing region in the request.

For example:

* Grid A has default region `us-east-1` and Grid B has default region `us-west-1`.
* A client sends a CreateBucket request to `s3.example.com` with `--region us-west-1`.
* Round-robin DNS directs the request to Grid A.
* Grid A routes the request to Grid B.
* The bucket is created on Grid B.

Additional considerations for CreateBucket:

* The `LocationConstraint` element can be set to any of the grid's default or non-default regions. This affects only ILM policy, not which grid creates the bucket (unlike AWS behavior with `us-east-1`).
* The signing region in the request determines which grid creates the bucket (signing region has to match the grid's default region).
* Presigned V4 requests are supported.
* Anonymous and V2 requests aren't supported for global namespace routing.
* ListBuckets requests sent to the global namespace endpoint are routed similarly to CreateBucket requests, using the signing region to determine the correct grid.
* Neither HEAD Bucket nor ListBuckets responses include the grid's default region. The default region is implied by the signing region, which is enforced to match the grid's default region.

TIP: StorageGRID doesn't enforce unique bucket names across grids in the global namespace.

== Configure DNS resolution

StorageGRID doesn't provide a built-in DNS resolver for global namespace. You must configure your external DNS infrastructure to route S3 requests to the correct grid.

Your DNS resolver should:

. Resolve the global namespace endpoint (for example, `s3.example.com`) to the load balancer endpoints of one or more grids, typically using round-robin DNS.

. Resolve each grid's unique CNAME (for example, `s3.grid-a.netapp.com`) to the load balancer endpoints for that specific grid.

. For virtual-hosted-style bucket requests (for example, `_bucket_.s3.example.com`), determine which grid owns the bucket and resolve to the correct grid's CNAME.
+
To determine which grid owns a bucket, the DNS resolver can query each grid for its bucket list and use the bucket's UUID (a time-based UUID that provides ordering) to identify the grid where the bucket was created.

== Account and access key management

Tenant accounts and S3 access keys can be synchronized across all grids using link:grid-federation-what-is-account-clone.html[account clone], but global namespace also works when each grid has its own separate set of access keys. If you use separate access keys, ensure that the S3 client uses the correct access key when sending requests to each grid.
